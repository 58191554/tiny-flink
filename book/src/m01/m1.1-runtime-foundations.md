# M1.1: Runtime Foundations

Before a runtime can execute a pipeline, it needs a vocabulary: which object are
we referring to, is its execution still active, and does an incoming message
contain data or signal completion? In this lesson, you will implement the small
types that answer those questions.

## What you will build

| Step | Header | Result |
| --- | --- | --- |
| 1 | `src/core/id.h` | IDs that distinguish different object categories at compile time |
| 2 | `src/core/job_status.h` | The lifecycle status of a whole job |
| 3 | `src/core/task_state.h` | The execution state of one task |
| 4 | `src/core/record.h` | A typed wrapper around one data value |
| 5 | `src/core/stream_message.h` | A message containing either data or an end-of-input signal |

## A job describes the whole computation; tasks execute its parts

Imagine a program that reads the numbers `1, 2, 3`, doubles each number, and
collects `2, 4, 6`:

```text
Read numbers  -->  Multiply by two  -->  Collect results
```

A **job** is the submitted computation as a whole. It includes the connected
processing steps and has an overall lifecycle. Asking whether the job succeeded
means asking whether the entire computation completed successfully.

A **task** is a runtime unit that executes part of that computation. It has its
own lifecycle. In a later, deliberately simple execution model, the example can
become a source task, a map task, and a sink task. A source may finish producing
data while the sink is still consuming it. The source task is then finished,
but the job is still running.

> See the real [Flink glossary](https://nightlies.apache.org/flink/flink-docs-stable/docs/concepts/glossary/).

### A preview of the two graph layers

We will introduce the graph classes in later lessons. For now, distinguish
**what should happen** from **what will execute it**:

```text
Logical graph:     Operator A  ---- Edge ---->  Operator B
                       |                           |
                  translated                  translated
                       |                           |
Execution graph:    Task A   ---- TaskEdge --->   Task B
```

This sketch assumes one task per operator. It is a teaching example, not a
general mapping rule. Parallelism can create multiple tasks for one logical
operator; chaining can place multiple operator instances inside one task.
Flink supports chaining and executes each task on a thread, as explained in
[Tasks and Operator Chains](https://nightlies.apache.org/flink/flink-docs-release-2.0/docs/concepts/flink-architecture/#tasks-and-operator-chains).
We will choose Tiny Flink's execution policy when we implement its runtime.

| Tiny Flink term | Meaning here | Related Apache Flink terminology |
| --- | --- | --- |
| Job | The entire submitted computation | Job |
| Operator | A logical processing step | Operator; a stream graph node is a `StreamNode` |
| Edge | A logical connection between steps | A stream graph connection is a `StreamEdge` |
| Task | An executable unit | Task / parallel subtask; represented in the execution graph by an `ExecutionVertex` |
| TaskEdge | A connection between executable units | Producer/consumer connections involving intermediate result partitions |

> Flink has more intermediate graph layers than this sketch. In particular,
> `StreamGraph`, `JobGraph`, and `ExecutionGraph` are distinct internal structures.
> The [`StreamEdge` source](https://github.com/apache/flink/blob/master/flink-runtime/src/main/java/org/apache/flink/streaming/api/graph/StreamEdge.java)
> and [`ExecutionVertex` API](https://nightlies.apache.org/flink/flink-docs-release-2.0/api/java/org/apache/flink/runtime/executiongraph/ExecutionVertex.html)
> are useful reference points. Older Flink versions also expose an
> [`ExecutionEdge` class](https://nightlies.apache.org/flink/flink-docs-release-1.9/api/java/org/apache/flink/runtime/executiongraph/ExecutionEdge.html),
> but `TaskEdge` is Tiny Flink's name; do not assume it is a current Flink class
> with the same API.

## Step 1: Give different objects different ID types

Start with `src/core/id.h`. We will need identities for operators, logical
edges, tasks, and execution edges. Their numeric values can use the same
representation, but their meanings must stay separate.

### Why a plain integer is insufficient

Wrap the number in `StrongId<Tag>` to distinguish ID categories at compile time.
The tag is a type-level label:
`StrongId<OperatorIdTag>` and `StrongId<TaskIdTag>` are different C++ types,
even when both store the same number.

### Implementation contract

Use the public API already established by `id.h`. Then declare four empty tag structs and their aliases:

| Tag struct | Public alias | Object category |
| --- | --- | --- |
| `OperatorIdTag` | `OperatorId = StrongId<OperatorIdTag>` | Logical operator |
| `EdgeIdTag` | `EdgeId = StrongId<EdgeIdTag>` | Logical edge |
| `TaskIdTag` | `TaskId = StrongId<TaskIdTag>` | Runtime task |
| `TaskEdgeIdTag` | `TaskEdgeId = StrongId<TaskEdgeIdTag>` | Execution connection |

Strong typing prevents category mistakes. It does **not** allocate IDs or
guarantee that two tasks receive different numeric values. ID allocation is a
separate responsibility. There is no `JobId` alias in the current header;
follow the four existing categories for this exercise.

**Checkpoint:** inspect `src/core/id_test.cpp`. 

## Steps 2 and 3: Describe job and task lifecycles

An ID answers which object. A status answers what is happening to it.

These states describe execution progress. They are different from an operator's
application state, such as a running sum or a keyed counter.

### JobStatus: the whole computation

In `src/core/job_status.h`, define `enum class JobStatus` with the following
enumerators, in this order:

| Status | Meaning | Terminal? |
| --- | --- | --- |
| `CREATED` | The job exists; execution has not started. | No |
| `RUNNING` | Execution is active; individual tasks may be at different stages. | No |
| `FINISHED` | All required tasks have completed successfully. | Yes |
| `FAILING` | Failure handling is in progress; remaining work is being stopped. | No |
| `FAILED` | Execution has ended with failure. | Yes |
| `CANCELLING` | Cancellation was requested; stopping work is still in progress. | No |
| `CANCELLED` | Execution has ended through cancellation. | Yes |

Implement `constexpr bool is_terminal_status(JobStatus status) noexcept`.
Return `true` only for `FINISHED`, `CANCELLED`, and `FAILED`.

These simplified paths illustrate the intent:

```text
Normal completion: CREATED --> RUNNING --> FINISHED
Failure:           RUNNING --> FAILING --> FAILED
Cancellation:      RUNNING --> CANCELLING --> CANCELLED
```

> Flink's [`JobStatus` enum](https://github.com/apache/flink/blob/master/flink-core/src/main/java/org/apache/flink/api/common/JobStatus.java)
> uses the same core concepts and also includes statuses for initialization,
> restarts, suspension, and reconciliation. Tiny Flink omits those mechanisms in
> this lesson. Flink spells its cancellation statuses `CANCELLING` and
> `CANCELED`; Tiny Flink's existing code uses `CANCELLING` and `CANCELLED`.

### TaskState: one executable unit

In `src/core/task_state.h`, define `enum class TaskState` with these enumerators,
in this order:

| State | Meaning | Terminal? |
| --- | --- | --- |
| `CREATED` | The task exists but has not started executing. | No |
| `RUNNING` | The task is executing, including waiting for more input. | No |
| `FINISHED` | The task completed its work successfully. | Yes |
| `CANCELLING` | The task is stopping in response to cancellation. | No |
| `CANCELLED` | The task has stopped through cancellation. | Yes |
| `FAILED` | The task's execution ended with an error. | Yes |

Implement `constexpr bool is_terminal_state(TaskState state) noexcept`.
Return `true` only for `FINISHED`, `CANCELLED`, and `FAILED`. Notice that
`TaskState` has no `FAILING` state: the job needs a separate coordination phase
for handling failures across its tasks.

```text
Normal completion: CREATED --> RUNNING --> FINISHED
Failure:           RUNNING --> FAILED
Cancellation:      RUNNING --> CANCELLING --> CANCELLED
```

>  Flink calls the corresponding enum
> [`ExecutionState`](https://github.com/apache/flink/blob/master/flink-runtime/src/main/java/org/apache/flink/runtime/execution/ExecutionState.java).
> It also models scheduling, deployment, initialization, and reconciliation.
> Its actual cancellation enum constants are `CANCELING` and `CANCELED`, while
> Tiny Flink uses `CANCELLING` and `CANCELLED`. Keep Tiny Flink's existing spelling
> in your implementation.

### Keep the two levels separate

For the three-task example, this is a valid intermediate snapshot:

| Object | Current state or status |
| --- | --- |
| Source task | `TaskState::FINISHED` |
| Map task | `TaskState::RUNNING` |
| Sink task | `TaskState::RUNNING` |
| Whole job | `JobStatus::RUNNING` |

## Step 4: Represent one piece of data with `Record<T>`

The job is now identifiable and its progress can be described. What does it
process? A **record** contains one application value: a number, a string, or a
user-defined event object.

Implement `Record<T>` in `src/core/record.h`.

### Implementation hints

Take the payload by value, then initialize `value_` with `std::move(value)`.
This allows a copyable lvalue to be copied into the parameter and an rvalue to be moved. It also supports payloads that can be
moved but cannot be copied, such as `std::unique_ptr<int>`.

Do not implement a universal deep-copy policy. A string copies its contents,
a shared pointer shares its pointee, and a unique pointer transfers ownership.
The accessor exposes a const reference to the stored `T`; this does not make
an object reached through a pointer deeply immutable.

Let the compiler generate the appropriate copy and move operations from the
member type. Avoid adding a custom destructor or copy constructor that would
accidentally suppress implicit move support. No default constructor is required,
and the payload type does not need a default constructor.

### Why introduce a wrapper?

`Record<int>{42}` identifies a data item explicitly. A separate wrapper also
gives the runtime a place to attach metadata later. 

>  Flink's corresponding type is [`StreamRecord<T>`](https://raw.githubusercontent.com/apache/flink/release-2.0/flink-runtime/src/main/java/org/apache/flink/streaming/runtime/streamrecord/StreamRecord.java),
> which includes a value and an optional timestamp. Tiny Flink's current
> `Record<T>` stores only the value; timestamps are outside this exercise.

**Checkpoint:** use `src/core/record_test.cpp`. 

## Step 5: Separate data from control with `StreamMessage<T>`

Consider what the sink sees after consuming the last number. An empty queue
cannot tell it whether more data will arrive later or the source is finished.
The runtime needs an explicit completion signal.

In `src/core/stream_message.h`, declare an empty marker type named `EndOfInput`
and a template alias named `StreamMessage<T>` with exactly these alternatives:

```text
StreamMessage<T>
    +-- Record<T>     : one application data value
    +-- EndOfInput    : no more records will arrive on this input
```

Use `std::variant<Record<T>, EndOfInput>` to represent these two alternatives.

In the later runtime, a normal finite input should obey this protocol:

```text
Record(1) --> Record(2) --> Record(3) --> EndOfInput
```

The signal follows all records on that input, and no more records follow it.
A downstream task can finish normally after its required inputs end and its
remaining work completes. With multiple inputs, ending one input does not mean
all inputs have ended. An unbounded input may continue indefinitely.

`EndOfInput` indicates normal input completion. It does not request
cancellation, report an exception, or declare the entire job finished. The
variant only represents messages: future producers, channels, and tasks must
enforce ordering and completion rules.

> Flink also separates data and control, but does not use this exact two-way
> variant. Its [`StreamElement` hierarchy](https://nightlies.apache.org/flink/flink-docs-release-2.0/api/java/org/apache/flink/streaming/runtime/streamrecord/StreamElement.html)
> includes records and other elements, such as watermarks. Completion also
> involves runtime events such as
> [`EndOfData`](https://github.com/apache/flink/blob/master/flink-runtime/src/main/java/org/apache/flink/runtime/io/network/api/EndOfData.java).
> Tiny Flink's `EndOfInput` is a small local protocol, not an exact replacement
> for all of Flink's completion machinery.

**Checkpoint:** use `src/core/stream_message_test.cpp`.
